# 實驗：編修流程回測

2026-11-16。驗證 0.5.0 新增的結構編輯與文風編輯，以及改寫後的審稿者，照定義依序處理一篇稿件時，能不能抓到作者當時退回的問題。

## 做法

- 題目：vervecode.dev〈Pagefind 中文搜尋〉。交給作者的版本是 vervecode.dev 的 commit `9c33b443`，作者核可的版本是 `46ef4772`。作者當時的回饋：拿掉開發過程、標題改得直白、收斂主線、修正英式中文。
- 三個代理都用一般子代理執行，先讀 `agents/` 底下的定義檔，再照本文做，`${CLAUDE_PLUGIN_ROOT}` 換成 repo 路徑。結構與文風用 Opus，審稿用 Sonnet，和定義檔相同。
- brief 只給讀者、讀者任務、語域、範圍外與不能改的內容，沒有篇幅參考與已核可的小標。代理不能讀 git 歷史、vervecode.dev 的檔案或已發佈的版本。
- 只跑結構、文風、審稿三步，沒有依審稿意見再修一輪。
- 稿件全文沒有存進 repo，用上面的 commit 可以重現。

- 結構編輯抓到的：開頭改從讀者看到的症狀寫起，作者導入的經過與實測細節移到實測紀錄，也指出標題的「Astro 部落格」把 Hugo 讀者排除在外。後兩項和作者的回饋一致。
- 結構編輯漏掉或做錯的：
  - 沒有刪「開發過程」一節，理由是它看起來像網站固定的 AI 揭露段，交給作者決定。作者刪了這一節。
  - 小標從 8 個增加到 9 個，作者收到 6 個。
  - 把開頭的具體例子「搜『模組』只找到 1 篇，實際有 14 篇」當成重複刪掉，作者保留了它。結構編輯的檢查清單第 1 項因此補上：開頭讓讀者對號入座的例子通常就是讀者第一次需要它的位置。
- 文風編輯改了約 33 句，其中 14 句是過度縮寫（「搜」改成「搜尋」），交接檢查沒有旗標。虛詞密度從 44.1 升到 45.9，仍比作者定稿的 52.6 低。
- 審稿者補上結構編輯漏掉的三點：「開發過程」和讀者任務無關、同一組數字在三處重複、標題限縮讀者。作者定稿正好處理了這三點。審稿也列出約 27 項，其中幾項是要作者補充的事實，建議寫法裡有一個它自己推測的指令，標了「待作者確認」。

## 結論

- 三步依序跑完，作者回饋的四類問題都至少被一步抓到，但結構編輯單獨跑時仍偏保守，要靠審稿與修正輪補上。所以 `review.md` 的修正輪不能省。
- 流程輸出的虛詞密度仍比作者定稿低。L2 的作者版本對照也有 7/16 題標 `glue-drop`，模型改寫的句子普遍比作者精簡，這是下一步要處理的方向。
