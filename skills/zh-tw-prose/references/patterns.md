# AI 腔模式目錄

寫完或改稿時對照這份目錄。每個模式都有五個部分：模式是什麼、為什麼讀者不舒服、怎麼改、前後例，以及什麼情況要保留。

改稿前先看「保留」。符合保留條件的寫法是對的，不要改。

單一句型不能證明文字是 AI 寫的，人寫的文字也會出現這些句型。判斷的依據是這個句型在這裡有沒有內容支撐，沒有支撐才改。

前後例只示範轉換方式，不要照抄句子。後例裡的功能、數字與原因是為了示範而假設的。實際改稿時，原文沒有具體事實可以替換，就刪掉空泛的部分，或問使用者，不要自己補一個。

## 句法

### P01 電報式短句

- 模式：省掉主詞、助詞與連接詞，把句子壓成筆記。被要求「精簡」「簡短」時最常出現。
- 理由：讀者要自己補回「要、才會、如果」這些關係，容易誤讀。
- 改法：補回主詞、動作與關係詞。真正要精簡時，刪掉重複的資訊，而不是刪掉助詞。
- 前：`設定存檔，重開生效。`
- 後：`修改設定後要先存檔，重新開啟程式才會生效。`
- 前：`不夠時降一級。`
- 後：`數量不足時，等級會降一級。`
- 保留：表格儲存格、按鈕標籤、圖表上的短標註、commit 標題與變更紀錄的條目，這些位置本來就只放名詞或短語。

### P02 假對比

- 模式：先立一個讀者沒有的誤解，再否定它來製造轉折。常見形式有「不是……而是」「並非……而是」「與其說……不如說」「不僅……更」「不只是……更是」。
- 理由：讀者本來沒有那個誤解，轉折是製造出來的，讀起來像推銷。
- 改法：直接寫它是什麼、會造成什麼後果。
- 前：`快取不是單純的加速手段，而是一種架構決策。`
- 後：`快取會改變資料多久才更新，所以要在設計階段決定哪些頁面可以快取。`
- 前：`這個工具不僅能節省時間，更能提升團隊的協作品質。`
- 後：`這個工具會自動合併三個人的設定檔，不用再手動比對差異。`
- 保留：讀者確實有那個誤解，例如前文剛引用了錯誤說法，或在更正常見的錯誤觀念（「很多人以為 `git pull` 只會下載，其實它還會合併」）。這時寫明誤解是什麼。

### P03 三段排比

- 模式：三個等長、對稱的詞或句子並列，常出現在開頭、結尾與標語。
- 理由：節奏過分整齊，第三項常是湊數。
- 改法：只留有證據的那一項，寫成具體結果。
- 前：`新版本更快、更穩、更好用。`
- 後：`新版本的建置時間從 90 秒降到 20 秒，其他行為和舊版相同。`
- 保留：本來就剛好有三個並列事實，而且每一項都有內容，例如「支援 Windows、macOS 與 Linux」。

### P04 格言式收句

- 模式：段落結尾把前文收成一句像金句的概括，例如「說到底，工具只是手段」「每多一種寫法，就多一份維護成本」。
- 理由：前文已經說明，再收一次是重複，而且口氣像在教訓人。
- 改法：直接刪除。段落需要收束時，改成一個具體的條件或下一步。
- 前：`改用環境變數後，部署時不必再改程式碼。說到底，設定和程式本來就該分開。`
- 後：`改用環境變數後，部署時不必再改程式碼。`
- 保留：全文的結論段需要給出判斷時，用具體條件寫判斷，例如「團隊少於五人時，先不用導入這套流程」。

### P05 一句塞太多概念

- 模式：一句同時定義名詞、說明輸入、交代結果與限制。
- 理由：讀者讀到句尾已經忘了句首。
- 改法：一句一個重點，拆成兩三句，用連接詞接回因果。
- 前：`PreToolUse hook 是在工具執行前由 Claude Code 呼叫、會收到 JSON 輸入並可用結束碼阻擋操作的腳本。`
- 後：`PreToolUse hook 是 Claude Code 在工具執行前呼叫的腳本。它會收到描述這次操作的 JSON，結束碼為 2 時，這次操作就會被擋下。`
- 保留：規格、合約與法規條文要把條件和結果寫在同一句，拆開後容易被斷章取義。

### P06 逗號切碎與句長太平均

- 模式：每個片語後面都加逗號，或連續幾句都是同樣長度的完整句。另一個極端是把逗號全部改成句號，寫成一串碎句。
- 理由：逗號應該跟著語意停頓，不是跟著字數。長短一樣的句子讀起來像機器在念。
- 改法：同一個動作或連續的步驟用「並、再、就、和」連成一句。資訊密集的段落之後，用一句短句收束或轉向。
- 前：`安裝完成後，開啟終端機，輸入指令，確認版本。`
- 後：`安裝後開啟終端機，輸入指令確認版本。`
- 保留：條列與步驟清單的每一項本來就是短句。一句裡的幾個項目各自需要停頓，例如逐項列出的警告或並列的名詞，用逗號或頓號分開。

## 語氣

### P07 提醒腔

- 模式：「值得注意的是」「需要注意的是」「記得」「最好先」「務必」「別忘了」。
- 理由：每段都有提醒，讀者會把提醒當成雜訊，真正危險的那一句反而被略過。
- 改法：把「為什麼要小心」寫成後果或條件。
- 前：`值得注意的是，修改前最好先備份。`
- 後：`這個指令會直接覆蓋原檔，不會留下備份。`
- 保留：安全或資料遺失的警告，而且已經寫出後果。這時可以用「注意」開頭，但只寫一次。

### P08 說教

- 模式：告訴讀者應該怎麼想或怎麼做才對，例如「分清楚才能用得好」「本質上」「我們要記住」。
- 理由：讀者沒有要求被教育，這類句子也不提供新資訊。
- 改法：只寫設定是什麼、會發生什麼，讓讀者自己做結論。
- 前：`分清楚 Volume 和 Bind Mount 的差異，才能真正用好 Docker。`
- 後：`Volume 的位置由 Docker 管理，Bind Mount 直接掛載主機上指定的資料夾。`
- 保留：讀者明確要建議或做法時，可以寫「建議」，但要寫出條件與理由，例如「不想依賴主機的資料夾結構時，用 Volume」。

### P09 推銷與空泛好處

- 模式：「無限可能」「輕鬆上手」「帶你一步步完成」「大幅提升體驗」「讓你的工作流程更順暢」。
- 理由：沒有具體內容的好處會讓讀者懷疑整篇的可信度。
- 改法：寫出具體結果與數字。沒有數字就刪掉評價，只寫事實。
- 前：`這個外掛能讓你的開發體驗更上一層樓。`
- 後：`這個外掛會在存檔時自動排版，不用再手動執行格式化指令。`
- 保留：使用者要寫產品介紹或推廣文案時，可以把好處放在前面，但每個好處都要對應到一個功能或數字。

### P10 評價詞

- 模式：「至關重要」「不可或缺」「關鍵」「非常實用」「寫得很清楚」「完美解決」。
- 理由：評價由作者宣稱，讀者無法驗證。
- 改法：把「為什麼重要」寫成後果。
- 前：`正確設定時區至關重要。`
- 後：`伺服器時區設成 UTC 時，原本要在台灣時間早上 9 點執行的排程，會延後 8 小時才執行。`
- 保留：評價後面緊接著寫出依據時可以留，例如「這一步不能省：少了它，資料庫遷移會中途失敗」。「關鍵字」「主鍵」「關鍵路徑」這類術語不是評價。

### P11 假真誠與附和

- 模式：「說真的」「老實說」「好問題」「你並不孤單」「我完全理解你的困擾」。
- 理由：這類開場只是在拉近距離，不提供資訊，讀者要讀到後面才拿到答案。
- 改法：直接回答。
- 前：`好問題！老實說，這個錯誤很多人都遇過。`
- 後：`請貼出完整的錯誤訊息和 node -v 的結果，我先確認是不是 Node 版本的問題。`
- 保留：社群貼文與個人隨筆裡，作者真的在表達自己的看法，而且後面接著具體內容。

### P12 模糊歸因

- 模式：「很多人認為」「業界普遍」「專家指出」「研究顯示」，卻沒有說是誰、哪一份研究。
- 理由：讀者無法查證，也無法判斷說法的分量。
- 改法：寫出來源與年份並附連結，或改成可以追溯的具體情境，例如「第一次安裝時常遇到」。找不到來源就刪掉。
- 前：`很多人認為 Rust 很難學。`
- 後：`Rust 要求每個值只有一個擁有者，把同一個變數傳給兩個函式時，要寫明是借用還是轉移。`
- 保留：官方文件或標準裡可以直接查到的通則，例如「HTTP 是無狀態的協定」。後面緊接著寫出出處時，例如「官方文件建議……」並附連結。

### P13 過度強調意義

- 模式：「標誌著」「象徵著」「開啟了新紀元」「重要的里程碑」「深遠的影響」。
- 理由：把一般的變更寫成歷史事件，讀者會覺得誇大。
- 改法：寫實際改變了什麼、影響了誰。
- 前：`這次更新標誌著專案進入了全新的階段。`
- 後：`這次更新把設定檔從 JSON 改成 TOML，舊設定會在第一次啟動時自動轉換。`
- 保留：真的是重大轉折，而且寫出改變了什麼，例如「1.0 之後，小版本更新不會再改動公開的 API」。

## 篇章

### P14 公式化開場

- 模式：「在當今瞬息萬變的時代」「隨著科技的快速發展」「在這個資訊爆炸的年代」。
- 理由：這類開場可以套在任何文章前面，等於沒有寫。
- 改法：從讀者遇到的問題或場景開始，第一句就給答案方向。
- 前：`隨著容器技術的普及，越來越多開發者開始使用 Docker。`
- 後：`Docker 容器裡的程式寫不進掛載目錄，多半是容器內的使用者 ID 和主機上的檔案擁有者對不上。`
- 保留：文章本身就在談趨勢或歷史時，背景是內容的一部分，但要寫具體的年份與事件。

### P15 自我導覽與編輯語言

- 模式：「本文將介紹」「接下來我們會」「以下是重點整理」「如上所述」「本節說明」。
- 理由：讀者看標題與段落就知道走向，導覽句只佔版面。
- 改法：刪掉導覽句，段落之間用內容銜接。需要指涉前文時，直接點出主題，例如「前面設定的 Volume」。
- 前：`本文將介紹如何在 Windows 上安裝 Node.js，接下來我們會一步步說明。`
- 後：`在 Windows 上可以用官方安裝程式或 winget 安裝 Node.js。`
- 保留：很長的參考文件可以有目錄，但目錄不需要一段話來介紹。界定範圍並附連結的句子也可以留，例如「權限設定不在這頁說明，見〈權限〉」。

### P16 首先、其次、最後

- 模式：每段都用「首先」「其次」「再者」「最後」開頭，不管內容有沒有先後關係。
- 理由：機械的骨架讓文章像作文範本。
- 改法：真的有順序時用編號步驟。沒有順序時，依重要程度排，段落開頭直接寫主題。
- 前：`首先，SQLite 不用架伺服器。其次，SQLite 只有一個檔案。最後，SQLite 很適合測試。`
- 後：`SQLite 的資料庫只是一個檔案，不用另外架伺服器，所以很適合在測試時每次重建。`
- 保留：內容真的有先後順序、又不適合寫成編號步驟時，例如在段落裡交代兩三個動作，可以用「先……再……最後」。

### P17 套話結尾

- 模式：「綜上所述」「總而言之」「總的來說」「希望本文對你有幫助」「歡迎留言討論」「未來可期」「讓我們拭目以待」。
- 理由：結尾套話不提供資訊，還會讓讀者懷疑前面的內容也是套出來的。
- 改法：用具體結論收尾，或寫讀者下一步可以做什麼。沒有新的結論就直接結束。
- 前：`綜上所述，只要設定好快取，網站效能就能大幅提升。希望本文對你有幫助！`
- 後：`設定好後重新整理頁面，開發者工具的 Network 面板會顯示回應來自快取。`
- 保留：正式文件的禮貌結尾，例如公告在說明影響之後寫一次「造成不便，敬請見諒」，見 [registers/formal.md](registers/formal.md)。社群貼文結尾可以留一個真正想問讀者的問題。

### P18 沒有立場

- 模式：「各有優缺點」「因人而異」「視情況而定」「端看你的需求」，後面沒有交代是哪些情況。
- 理由：讀者想知道該怎麼選。
- 改法：寫出條件與選擇，例如「單人專案選 A，要多人協作時改用 B，因為 B 才有權限控管」。真的取決於讀者的條件時，列出那些條件。
- 前：`SQLite 和 PostgreSQL 各有優缺點，選擇哪一個端看你的需求。`
- 後：`單機的小工具用 SQLite，不必另外架伺服器。寫入很頻繁，或要讓多台機器連同一份資料時，改用 PostgreSQL。`
- 保留：資訊真的不足以判斷時，寫明缺的是哪一項，例如「要看資料量會不會超過單機記憶體」。

### P19 假範圍

- 模式：「從初學者到專家都適用」「從個人到企業」「從前端到後端」，兩端其實沒有關係，只是用來顯得涵蓋面廣。
- 理由：讀者無法從這句判斷內容是否適合自己。
- 改法：寫出真正的前提，例如「本文的步驟需要會用 Git 的基本指令」。
- 前：`這份教學從新手到資深工程師都適用。`
- 後：`這份教學假設你會用終端機執行指令，不需要寫過 Go。`
- 保留：兩端真的都有具體內容，例如「每個範例都提供 JavaScript 與 Python 兩個版本」。

## 格式

### P20 過度條列

- 模式：每個想法一行、每行一句，或把有因果關係的段落拆成清單。
- 理由：條列會切斷因果，讀者看到一堆並列的點，卻不知道它們之間的關係。
- 改法：真正並列、互相獨立的項目才用條列。有因果、條件與判斷的內容寫成段落。連續幾個小節都是標題後直接接條列，而且條列之間其實有因果或條件關係時，至少改寫一節。
- 前：三行條列「快取過期」「頁面顯示舊資料」「要清除 CDN」，彼此的因果關係沒有寫出來。
- 後：`快取過期前，頁面會繼續顯示舊資料，所以改版後要清除 CDN 快取。`
- 保留：真正並列、互相獨立的項目，例如支援的平台與檔案格式、設定選項、操作步驟。

### P21 粗體與 emoji

- 模式：一段裡有好幾處粗體、整句粗體、條列每行用粗體開頭，或用 emoji 當標題與項目符號。
- 理由：處處強調等於沒有強調，emoji 標題在台灣的技術與正式文件裡顯得輕浮。
- 改法：粗體只留給讀者掃描時必須找到的少數詞，或完全不用。不用 emoji 當結構記號。
- 前：`**重要：** 請 **務必** 先 **備份資料**。`
- 後：`升級會改寫資料庫結構，而且無法還原，請先備份資料。`
- 保留：參考文件裡讀者掃描時要找的少數詞，例如設定名稱。社群貼文可以依平台習慣用 emoji，但不當成標題或項目符號。

### P22 標題不像標題

- 模式：標題寫成口語動詞片語（「怎麼救回來」「從哪來」）、直譯的介詞片語（「用於」「取得自」），或空泛的概括（「為什麼這樣有效」「關鍵在這裡」）。
- 理由：標題是讀者掃描時的路標，要能單獨看懂。
- 改法：用該領域的名詞，例如「處理方式」「來源」「用途」「效能比較」。標題要能看出這一節講什麼。
- 前：`## 怎麼救回來`
- 後：`## 復原方式`
- 保留：FAQ 的標題本來就是讀者的問題，可以寫成問句，例如「為什麼收不到驗證信？」。

### P23 講義式冒號

- 模式：句子開頭先放一個詞加冒號，例如「重點：」「結論：」「關鍵在於：」，或連續幾段都用冒號引出。
- 理由：讀起來像投影片，不像文章。
- 改法：寫成完整句。
- 前：`重點：快取要設定過期時間。`
- 後：`快取要設定過期時間，否則改版後使用者會一直看到舊頁面。`
- 保留：表格、定義清單、欄位說明，以及「時間：11 月 8 日」這類資訊欄位。

## 用詞

### P24 成語與書面詞堆疊

- 模式：「舉足輕重」「脫穎而出」「如虎添翼」「事半功倍」「與時俱進」連續出現。
- 理由：成語越多，資訊越少，讀起來像作文。
- 改法：換成具體描述。一段裡最多留一個真正貼切的成語。
- 前：`這個框架讓開發事半功倍，在眾多工具中脫穎而出。`
- 後：`這個框架內建路由與表單驗證，不用再另外裝套件。`
- 保留：讀者熟悉、換成白話會變長又不準確的成語，例如「一勞永逸」。

### P25 書面腔

- 模式：在一般說明文裡把「予以」「藉由」「於」「之」「該」「此」「係」當虛詞用。
- 理由：台灣讀者讀技術文章與介面時，期待像同事說話的平實口吻。
- 改法：「予以啟用」改成「啟用」，「藉由」改成「透過」或「用」，「於設定頁」改成「在設定頁」，「該功能」改成「這個功能」。「進行」這類虛動詞見 [translationese.md](translationese.md) 的 T01。
- 前：`該功能須於設定頁予以啟用。`
- 後：`這個功能要在設定頁啟用。`
- 保留：本來就含這些字的一般詞彙，例如「此外」「之後」「三分之一」「位於」「屬於」「關於」。正式文件語域的公告、規章與法律文字，見 [registers/formal.md](registers/formal.md)。
