# 語域：技術文章

讀者是想完成一個任務或弄懂一個問題的工程師，常常從搜尋引擎直接進到這篇。部落格、教學、技術筆記、排錯紀錄都用這個語域。

## 讀者與口吻

- 像對同事說明：平實、直接、可信。不用驚嘆句、導購式開場或「今天要跟大家分享」。
- 人稱以「我們」帶讀者理解問題。「我」只用在交代作者自己的經驗、除錯轉折或判斷依據。「你」少用，適合寫讀者的判斷條件，例如「如果你的專案要支援離線」。
- 排錯現場可以下直接的判斷，例如「八成是權限沒對上」，這比「建議進一步確認權限設定」更能幫讀者決定先查哪裡。介紹文與還沒驗證的說法要保守。
- 不教育讀者，不寫「分清楚才能用得好」。

## 開頭

- 第一段依序寫讀者遇到的問題或想做的事、這篇讓讀者做到什麼，以及理解後文需要的概念。做法的細節、版本、指令與路徑放到後面的段落。不用「本文會介紹」解釋文章架構。
- 前：`本文將說明 Docker Volume 的權限問題，以及幾種常見的解決方式。`
- 後：`容器裡的程式寫不進掛載目錄，多半是容器內的使用者 ID 和主機上的檔案擁有者對不上。把容器的使用者改成和主機相同的 UID，就能正常寫入。`
- 標題、摘要（front matter 的 summary、description）與第一段寫整篇要傳達的概念，最多點名主角工具。主角工具是讀者認得的產品或套件，資料夾、檔名、設定檔與指令參數不算。作業系統、硬體、套件版本、指令、檔名與路徑都不放進來，讀者還不知道這篇要解決什麼，就先讀到一串規格與檔名。這些放在哪裡，見「內容取捨」。標題冒號後面寫讀者的問題或得到的結果，文章縮圖上的字也一樣。
  - 前：`我在 Ubuntu 24.04、Node 22.11 與 pnpm 9.12 的環境下，用 vite-plugin-pwa 0.21 加上離線快取。`
  - 後：`網站加上 Service Worker 後，斷網也能打開造訪過的頁面。用 Vite 的 PWA 外掛只要改設定檔，不用手寫 Service Worker。`
  - 前（標題）：`Docker Compose 多環境設定：用 compose.override.yaml 與 --env-file 切換`
  - 後（標題）：`Docker Compose 多環境設定：本機開發與正式部署共用一份設定`
- 標題寫成「主題：讀者得到的結果」，不寫成一句指示或描述。結果用正面說法，產品名只留主角。
  - 前（標題）：`用 Docker 跑 PostgreSQL，記得先掛載資料夾再開始寫入資料`
  - 後（標題）：`Docker 執行 PostgreSQL：容器重建後資料仍然保留`
  - 前（標題）：`Git LFS 管理大檔案：不必再讓 repo 越來越大`
  - 後（標題）：`Git LFS 管理大檔案：repo 只存指標，clone 只下載需要的版本`
- 保留：讀者要找的就是版本、指令或那個檔案本身（「Node 22 怎麼裝」、升級指南、破壞性變更、`.gitignore` 的寫法），這時它們是讀者的搜尋詞，開頭與標題直接給。排錯文要讓讀者比對錯誤訊息與環境，錯誤訊息裡有檔名時，開頭也直接給。
- 第一段的寫法和其他段一樣，從讀者的情況切入，見「結構」。
- 使用者交代的概念句（「重點是它能把試算表當資料庫用」）是要傳達的意思，不是要貼上的句子。找出那句話背後的具體物件與因果，用素材裡的事實寫成讀者沒有背景也看得懂的段落。素材不夠展開時，先問使用者那句話具體指什麼，不自己補功能。使用者指定的標語或開場句、引述的原話，以及本身已經說得完整的句子，照原樣用。

## 內容取捨

- 每一段都服務讀者的任務，無關的背景、規格與延伸說明直接刪掉。作者實際測過、但偏離讀者任務的旁支（順手試的另一種設定、和主題無關的發現）也刪掉，值得寫就另寫一篇。
- 操作教學只交付標題承諾的任務。
- 文章沒做到的事不寫。作者沒做過的情境（其他安裝方式、其他平台、其他版本）不照官方文件補進正文，也不用「沒有實測」「照官方文件整理」交代範圍，整句刪掉。
  - 前：`設定檔放在專案根目錄。用 Homebrew 安裝的版本，設定檔則在 /opt/homebrew/etc 底下。……以上 Homebrew 的部分照官方文件整理，沒有實測。`
  - 後：`設定檔放在專案根目錄。`
  - 保留：讀者的任務就落在那個情境、文章沒寫就完成不了時，實測後再寫，不只補官方說法。比較文與評測的「尚未驗證」清單，讀者要靠它判斷結論適用到哪裡。資料遺失、金錢或安全相關的限制，沒有實測也要寫明並附來源。
- 每篇都要讓讀者能確認自己做對了，例如成功時的畫面、輸出或數字。
- 環境與版本依讀者什麼時候需要分開寫。決定「這篇適不適用我」的條件（作業系統、硬體、瀏覽器、成品規格）寫在開頭之後的獨立一段。開始前要準備的東西（權限、需要的檔案、要先裝的工具）集中在第一個步驟之前。套件的詳細版本、指令、檔名與路徑寫在用到它的步驟旁邊。
- 不拿讀者沒看過的教學當對照（「舊教學」「常見的教學」），改寫成讀者做過的事或版本差異，見 patterns.md 的 P12。
- 不重述官方文件。需要時引用並附連結，正文只寫官方文件沒寫的判斷與實作。

## 術語

- 讀者慣用英文的技術術語保留原文，例如 API、Token、Commit、Container、Header。不要硬翻成「令牌」「標頭」。
- 專有名詞第一次出現時用一句話說明，例如「總開關（Kill Switch）」。
- 一般中文詞照常使用，例如請求、回應、門檻、像素。
- 產品有正體中文介面時，操作步驟用介面上看得到的字並加「」，讀者照著文章才找得到同一個按鈕。工具內部或 API 的叫法第一次出現時，對應到介面上的位置。不確定介面怎麼寫，就切換到正體中文介面看一次，或查產品的在地化字串檔，不憑印象翻。
  - 前：`打開 Layers panel，把背景 layer 的 visibility toggle 關掉。`
  - 後：`打開「圖層」面板，把背景圖層的「顯示」關掉。`
- 產品沒有正體中文介面時，用英文介面上的原字並加「」。讀者多半用英文介面時，寫英文原字，第一次出現附上中文介面的名稱。討論 API 或設定檔本身時，用程式碼裡的名稱並加反引號。

## 結構

- 小標寫成名詞片語，同一篇的小標風格一致。
- 段落之間要有推進：前一段留下的問題是下一段的起點。
- 每段從讀者的情況、目標或下一步動作切入，再帶出工具的行為。從工具的內部機制或作者的測試過程切入，每句都對，讀起來卻像技術報告，讀者要自己把機制翻譯成「這跟我要做的事有什麼關係」。寫的時候逐項換成讀者的位置：
  - 起點寫讀者做了什麼、遇到什麼，不寫工具內部怎麼分類或判斷。
  - 解法寫讀者想達成的狀態，不寫成功能說明（「也支援……」）。
  - 動作寫讀者實際要做的步驟，不寫「用設定告訴它」這類抽象說法。
  - 理由寫讀者看得到的結果，不寫工具內部的判斷依據。
  - 工具的行為直接寫它做了什麼，不寫它「發現」「判斷」：「npm 發現 lock 檔過期，會重新解析相依套件」改成「lock 檔過期時，npm 會重新解析相依套件」。
  - 前：`Docker 依 Dockerfile 的每一行建立一層映像，某一層的輸入改變時，這層和之後的層都要重建。COPY . . 寫在 RUN npm install 前面，任何檔案改動都會讓安裝套件的那層失效。`
  - 後：`只改一行程式碼，重新建置卻又花五分鐘裝套件，是因為 Dockerfile 先複製整個專案才安裝套件。改成先複製 package.json 並安裝，再複製其餘程式碼，之後只改程式碼時，建置會直接沿用裝好的套件。`
  - 前：`Vite 只把 VITE_ 開頭的環境變數打包進前端程式碼，所以變數名稱要加上這個前綴。`
  - 後：`變數名稱要加上 VITE_ 前綴，前端程式碼才讀得到。`
  - 保留：讀者來找的就是機制本身，例如原理解說、架構設計文件、效能分析。排錯文要讓讀者理解成因時可以先講機制，但從讀者看到的症狀切入。實測紀錄與附錄裡的表格、測試條件本來就是報告體。
- 程式碼、圖片與表格前面寫一句說出內容的引言，例如「設定檔要加上這兩行：」，不寫「下表是……」。
- 結尾用一到兩段具體結論，不重述正文，也不放正文沒提過的新事實。沒有新的結論就直接結束。

## 長度

文章的長度由讀者任務決定，沒有固定字數。刪減後要確認必要的原因、步驟與銜接還在，不要為了變短刪掉讀者需要的條件。
