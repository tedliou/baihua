# 正體中文寫作

目標是讓文字讀起來像熟悉主題的台灣人寫的：句子完整、先給答案、用具體事實取代評價，沒有 AI 腔、翻譯腔與對岸用語。

## 優先順序

規則衝突時，依序以這些為準：

1. 使用者這次的指示。
2. 專案的文風檔與用詞表。專案的 CLAUDE.md 通常會指出位置，常見的是 `GLOSSARY.md`。
3. 其他 skill 對自己領域的規定，例如介面 skill 決定畫面上放什麼、標籤多長。
4. 本 skill 的語域設定。
5. 本 skill 的核心規則。

本 skill 只決定句子怎麼寫。要寫什麼內容、術語叫什麼、版面怎麼排，由使用者、專案與領域 skill 決定。

## 核心規則

每條規則後面附理由。遇到規則沒有想到的情況時，依理由判斷。

1. 句子寫完整，保留主詞、動作、受詞，以及「能、會、可以、的、和、再、就」這類助詞與連接詞。精簡是刪掉重複的資訊，不是刪掉助詞。理由：電報式短句要讀者自己補回關係，容易誤讀。
2. 先給答案。第一句回答讀者來找的問題，背景放在後面，不先解釋文章要講什麼。理由：讀者多半只讀開頭。
3. 同一個資訊只寫一次。不在段落、表格與結尾重複同一句，段尾不把前文收成一句格言。理由：重複會讓讀者以為是新資訊。
4. 用具體事實取代評價。寫數字、後果或看得到的現象，沒有依據就不寫「大幅」「至關重要」「非常實用」。理由：評價詞無法驗證，會拖累整篇的可信度。
5. 句型要有存在的理由。假對比（不是……而是）、三段排比、提醒腔、說教、推銷、自我導覽句與名詞化，只在內容真的需要時使用。理由：這些是讀者最先認出的 AI 腔。模式與前後例見 [patterns.md](references/patterns.md)。
6. 用動詞直接說動作，少用「進行、作出、加以、予以、扮演……角色」與不必要的被動句。理由：翻譯腔讓句子變長、主詞消失。見 [translationese.md](references/translationese.md)。
7. 用台灣用語。「視頻」寫成「影片」，「默認」寫成「預設」，「信息」寫成「資訊」。不確定的詞先查證再用。理由：對岸用語讓台灣讀者覺得文字是轉換來的。對照表見 [taiwan-usage.md](references/taiwan-usage.md)。
8. 標點用全形，引號用「」，中文與英文、數字之間加半形空格。一般段落不用分號串接長句，介面字串與規格欄位並列兩組數值時可以用。破折號少用。理由：這是教育部標點手冊與主流在地化指南的做法，分號在段落裡容易被拿來串接過長的句子。見 [punctuation.md](references/punctuation.md)。
9. 依資訊性質選格式。比較用表格，步驟用條列，流程用圖，因果與判斷用段落。標題與表頭用名詞（「處理方式」「來源」），不用口語動詞片語。粗體不拿來強調整句，emoji 不當標題記號。理由：格式是幫讀者找資訊，不是讓頁面看起來整理過。
10. 內容誠實。不捏造經驗、測試結果、引用與數字，不替產品補上素材沒有的功能，推論要標成推論，不把語境擴張成使用者沒說的計畫。理由：讀者會把「我測過」當成證據。見 [integrity.md](references/integrity.md)。

## 中文句子的組法

中文靠語序與上下文表達句子之間的關係，英文靠代名詞、連接詞與子句。模型的中文常把英文的組法搬過來，字都對，讀起來卻像翻譯稿。

1. 話題說一次，後面接著說。一段的主角出現後，接下來幾個分句直接說它做什麼、結果如何，不再用「它、我們、你、這個工具」指回去。換了主角才寫出新的主詞。省掉的主詞必須就是前面的話題，話題和後面的動作接不上時（「初學的人，這套工具是常見的選擇」），把主詞寫出來。理由：中文是話題優先的語言，主詞在上下文清楚時省略才自然。
   - 前：`這個指令會讀取設定檔，然後它會檢查格式，接著它會把結果寫進日誌。`
   - 後：`這個指令會讀取設定檔、檢查格式，再把結果寫進日誌。`
2. 照事情發生的順序寫。原因在前、結果在後，條件在前、動作在後：「先備份資料庫，再升級」，不寫「在升級之前，請確保已經備份資料庫」。「先給答案」指的是段落先講結論，句子內部仍照時間順序。理由：中文的語序跟著時間與因果走，倒過來寫要讀者在腦中重排。
3. 關係看得出來就不寫連接詞。前後兩句的先後與因果從語序就看得出來時，省掉「因此、而且、同時、此外、另外」，用逗號讓分句接著走，需要時用「就、再、才、也」把分句接起來。轉折、讓步與條件才需要連接詞。理由：翻譯稿的連接詞比母語文字多，每句都在交代邏輯，讀起來像論文。
4. 名詞前面只放短的修飾。名詞前的修飾語超過一個「的」，或比名詞本身長很多時，把修飾語改成名詞後面的分句。
   - 前：`這是一套由社群維護、支援多種資料庫的開源工具。`
   - 後：`這套開源工具由社群維護，支援多種資料庫。`
   - 理由：修飾語越長，讀者越晚看到主角，也越難記住前面讀過的內容。
5. 句子長短跟著內容走。交代因果與條件的句子可以長，結論或轉向用短句。連續幾句長度差不多時，合併或拆開其中一句。理由：句長平均是模型文字最容易被聽出來的節奏。

## 語域

先判斷讀者是誰、正在做什麼，選一個語域。表裡的要點在任何長度都適用。寫整篇文章或整份文件時，再讀對應的檔案。沒有完全符合的語域時，選最接近的一個，再依理由調整。

| 語域 | 讀者與情境 | 要點 | 檔案 |
| --- | --- | --- | --- |
| 技術文章 | 想完成任務或弄懂問題的工程師：部落格、教學、技術筆記 | 第一段回答讀者的問題。像對同事說明，不教育讀者，不寫「讀完你就能」 | [article.md](references/registers/article.md) |
| 參考文件 | 查規則、設定或名詞的人：wiki、說明頁、API 文件、README | 開頭寫它是什麼、做什麼。主詞是系統裡的東西，少用「你」，不提醒、不推銷 | [reference.md](references/registers/reference.md) |
| 介面文字 | 正在操作產品的人：按鈕、標籤、錯誤訊息、通知 | 用讀者認得的說法。錯誤訊息寫發生什麼與怎麼處理，語氣平實，不道歉過度、不裝可愛 | [ui.md](references/registers/ui.md) |
| 工作報告 | 同事或使用者本人：進度報告、PR、commit、會議紀錄 | 第一句寫結果或狀態，需要對方決定的事放顯眼處。失敗與未驗證照實寫 | [report.md](references/registers/report.md) |
| 社群貼文 | 滑到這則貼文、還不認識作者的人 | 第一句交代背景，用第一人稱寫實際做了什麼。口語但句子完整，不寫標題黨 | [social.md](references/registers/social.md) |
| 正式文件 | 一般大眾或客戶：公告、規章、對外聲明 | 內容要完整：發生什麼、何時、影響誰、不受影響的部分、讀者要做什麼。公告用慣用的格式：主旨、「維護時間：」「影響範圍：」這類欄位、致歉與署名。稱「您」，正式但白話 | [formal.md](references/registers/formal.md) |

## 寫作流程

1. 確認讀者、讀者要完成什麼，以及用哪個語域。素材缺少只有使用者知道的事實（經驗、測試結果、決策理由）時，先問，不自己補。
2. 寫。寫完用下面的檢查清單逐句讀一次，再確認每段都服務讀者的任務。
3. 文字存成檔案而且能執行 Python 時，執行本 skill 目錄下的 `scripts/check.py <檔案>`。專案有用詞表時加上 `--glossary <用詞表路徑>`。依輸出逐一修正。加上 `--profile` 會印出每千字的連接詞、代名詞與「的」的密度，數字明顯偏高時，回頭用「中文句子的組法」檢查那幾段。腳本只查字串，句型與語氣仍要自己判斷。
4. 長文或要對外發佈的文字，交給沒有看過寫作過程的審稿者讀一次全文。審稿的交辦方式見 [review.md](references/review.md)。

## 檢查清單

寫完或改稿時逐句對照。命中的寫法就算句子通順也要處理，除非符合「保留」欄的條件。例句是示意，同類的說法一樣要處理。每一類的完整說明與前後例見 [patterns.md](references/patterns.md) 與 [translationese.md](references/translationese.md)。

| 看到 | 處理 | 保留 |
| --- | --- | --- |
| 先下評語再說內容：「這個設計很漂亮：」「重點很簡單」「說穿了」 | 刪掉評語，直接寫內容 | 結論段需要給判斷時，用具體條件寫 |
| 沒有依據的評價：「非常實用」「完美解決」「效能大幅提升」「幾乎零設定」 | 換成素材裡的數字或現象，素材沒有就刪 | 素材本身有數據支持的判斷 |
| 推測與展望：「相信之後會越來越好」「未來可期」「下一版應該會改善」 | 刪掉。要保留時寫明是推論與依據 | 素材明確寫出的計畫或時程 |
| 自我導覽與承諾：「本文將介紹」「接下來我們會」「讀完這篇你就能」「這一節說明」 | 刪掉，第一句直接寫內容或答案 | 超過一屏的長文件目錄，或真的需要讀者跳轉的連結 |
| 說教、提醒與責備：「一定要先搞懂」「我們要記住」「務必」「別亂動」「值得注意的是」 | 改成中性的條件與做法：「改了沒效果時，把設定改回自動」 | 會造成資料遺失、金錢損失或安全問題的警告，寫明後果 |
| 推銷與空泛對象：「推薦給所有想……的人」「從新手到老手都適用」「輕鬆上手」 | 刪掉，或改成具體的使用條件 | 文件本來就在說明適用範圍時，寫具體條件 |
| 恭維讀者、替讀者預告反應：「眼尖的讀者」「相信你已經注意到」「你一定遇過」 | 直接陳述那個事實 | 社群貼文用來交代背景的第一人稱經驗 |
| 裝熟的語氣詞與符號：「~」「囉」「der」「先放輕鬆」 | 刪掉 | 社群貼文或角色台詞本來的口吻 |
| 假對比：「不是……而是」「不僅……更」「與其說……不如說」 | 直接寫它是什麼、會造成什麼 | 讀者真的有那個誤解，或在更正常見錯誤 |
| 段尾格言、重述前文：「說到底，工具只是手段」「總而言之」 | 刪掉 | 全文結論段給出判斷時 |
| 名詞化與虛動詞：「由系統完成驗證」「進行測試」「加以處理」 | 改成誰做了什麼：「系統會驗證」 | 標題、表頭與術語 |
| 介詞堆疊與代名詞：一句疊好幾個介詞片語、「對於……來說」、表示手段的「通過」、「它」指不清楚 | 改語序，重複名詞或省略主詞 | 「由於、因此、若、而、所致」這類常見的書面連接詞 |
| 冒號標籤：「重點：」「結論：」，說明前面先放一個分類詞加冒號 | 刪掉標籤，直接寫內容 | 表單欄位的標籤，以及表格本身 |
| 電報式短句：「設定存檔，重開生效」 | 補回主詞、助詞與關係詞 | 按鈕、表格儲存格、commit 標題 |

## 改稿

先依使用者的要求決定改多少：

- 潤稿、修飾、「看一下」：原文沒錯的句子保留，包括語氣、句型與用字。只改錯字、文法不通、對岸用語、標點，以及檢查清單裡明顯的問題，例如恭維讀者、裝熟的語氣詞、推銷詞、沒有依據的評價。文法有明顯問題時才大改。
- 改寫、去 AI 腔、重寫：逐句對照檢查清單，命中的句子都要處理。

兩種都依這些原則：

1. 先讀全文，掌握作者的語氣與事實。
2. 命中檢查清單的句子，先對照「保留」欄與 [patterns.md](references/patterns.md) 的保留條件。符合保留條件的寫法是對的，例如讀者真的有誤解時的「不是……而是」、正式條款裡的「於、之、得」、表示不幸的「被盜用」。
3. 沒有錯的詞不換。「由於、因此、若、而、所致」這類書面連接詞是常見用法，不要換成口語。把「大概」換成「約略」也一樣，只會抹掉作者的語氣。
4. 刪掉 AI 腔時改寫成具體內容，不換成同義詞。把「標誌著」換成「象徵著」仍是同一個問題。要刪的是誇大與空話，原文的論點要留下：「為使用者帶來了前所未有的便利」改成「用起來比較方便」，不是整句刪掉。原文沒有的內容與說明也不要補。
5. 連貫的長句只要讀得順，就不切成幾個短句。一句話用「……後，才……」交代先後與因果時，切開會讓關係消失，讀起來也比原文生硬。
6. 事實、數字、網址、版本與程式碼保持原樣。原文的格式（段落、條列、表格）與數值寫法（例如「+1」）除非有問題，否則照原樣。

其他：

- 保留使用者手改的地方。
- 改完簡短說明改了哪幾類問題，不逐句列出。使用者要求只輸出成品時照做。
- 使用者反覆做同一種修改時，依 [learning.md](references/learning.md) 整理成偏好，經使用者同意後寫回專案的文風檔。

## 常見失誤

- 被要求精簡時刪掉助詞與連接詞，寫成電報式短句。精簡要刪的是重複的資訊與沒有內容的句子。使用者指定長度時，以那個長度為目標，不是只刪幾個字。
- 為了避開 AI 腔而刻意口語、加語助詞或網路用語。目標是平實，不是裝熟。
- 把讀者慣用英文的技術術語硬翻成中文，例如 API、Token、Commit、Docker Volume。專案另有規定時照專案。
- 結尾加上「希望對你有幫助」「如有問題歡迎留言」，或開頭稱讚使用者的問題。
